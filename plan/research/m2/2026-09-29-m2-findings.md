# M2 findings — save, load, inspect, reuse (upstream DSPy 3.4.0)

Greta → Horst · 2026-09-29 · a findings package for slicing, **not a contract**. Upstream read by Pia (read-only scout); every load-bearing line below re-checked by Greta against `../dspy-3.4.0` (Pia's quotes were all verbatim; five of her line numbers drifted, corrected here).

## Your four questions, answered

1. **JSON or pickle?** **Both, and the split is clean.**
   - *State-only save* (`Module.save("x.json")` / `module.load("x.json")`) is **JSON** (`orjson`), chosen by the file extension (`primitives/base_module.py:229-234`). This is the documented path, and it contains only learned state — **no pickle needed for parity here.**
   - `.pkl` state (`base_module.py:241-247`) and **whole-program save** (`save_program=True` → `<dir>/program.pkl`, `base_module.py:204,217-218`; `dspy.load(dir)`, `utils/saving.py:61`) are **cloudpickle of live Python objects**, gated behind `allow_pickle=True` (`base_module.py:269`, `saving.py:40`).
   - **The hard wall is only whole-program save.** It serialises Python classes and code, which Elixir can neither read nor write. Recommend declaring it **not applicable**: our "whole program" is *our code plus a state file*.
2. **What is in the state?** `{"<sub-module path>": <predictor state>, …, "metadata": {"dependency_versions": {python, dspy, cloudpickle}}}` (`base_module.py:157-158,198-202,230-231`). Per predictor (`predict/predict.py:74-97`):
   - `traces`, `train`, `demos` (each demo as a dict of its fields, nested objects serialised);
   - `signature`: `{"instructions": …, "fields": [{"prefix", "description"}, …]}` (`signatures/signature.py:524-535`) — **no field names**;
   - `fields` (only if set);
   - `lm`: LM class name, `model`, `model_type`, `cache`, `num_retries` and the call kwargs, **minus `api_key`** (`clients/base_lm.py:217-237`).
   - **Not saved:** program structure, per-predictor `config` (temperature, `n`, `rollout_id`…), callbacks, history.
3. **What must round-trip for "load elsewhere and behave the same"?**
   - Upstream itself only round-trips *learned* state. "Behaves the same" also needs **the same code** (the structure and sub-module names come from code; `load_state` reads `state[name]` per named parameter, `base_module.py:160-172`), **the same `config`** (not saved), and **the same LM responses** (model plus cache, or a scripted LM in tests).
   - Upstream's own test is exactly this: `assert new_predict.dump_state() == predict.dump_state()` (`tests/utils/test_saving.py:177`), in 8 save/load tests in that file.
4. **Where the Elixir shape diverges** — six places, detailed below. The big one is **per-module history** (F-6): Python appends to a mutable list *on the module object*; our modules are immutable structs.

## Findings that shape the slicing

- **F-1. Positional field restore — upstream corrupts silently.** `Signature.load_state` applies saved prefixes and descriptions **by position**: `zip(signature_copy.fields.values(), state["fields"], strict=False)` (`signature.py:537-545`). If the code's signature gained, lost or reordered a field since the save, descriptions land on the wrong fields or are dropped, with no error. **Under our principle: raise.** Proposal: when *we* save, add each field's `name` next to `prefix`/`description`. Upstream's loader reads those two keys by name and ignores extra keys, so our files stay loadable upstream. When loading, match by name if names are present and raise on any mismatch; for upstream-written files (no names), require an equal field count and raise otherwise.
- **F-2. LM restore by class name.** Upstream stores the LM's qualified class name and rebuilds that class. It also **drops `api_base`, `base_url` and `model_list` unless the caller passes `allow_unsafe_lm_state=True`** (`predict.py:25-43`), because a state file must not redirect traffic. Elixir: the LM module name must come from an allowlist or `String.to_existing_atom/1` — never create an atom, and never pick an arbitrary module from file data (the B2/BB2 lesson, plus a security boundary). Port the unsafe-keys rule as is.
- **F-3. Loading is atomic upstream** (a trial run on a deep copy "raises before self is touched", `base_module.py:170-172`). We get this for free: `load` builds and returns a new struct, and the old one is untouched.
- **F-4. Unknown keys.** Upstream `setattr`s any extra key onto the predictor (`predict.py:124-127`). Elixir structs cannot take arbitrary fields. Proposal: ignore with a warning. That's not data loss — the file is untouched — so it isn't a principle case, but it needs your ruling.
- **F-5. Version metadata is warn-only upstream** (`saving.py:53`, `base_module.py:276-287`: a mismatch logs and continues). Proposal: record `dspy_ex`, Elixir and OTP versions, and warn on mismatch, as upstream.
- **F-6. `Module.inspect_history` — the real design problem (architecture; needs my co-sign, it touches process context).**
  - Upstream: every LM call is appended to `GLOBAL_HISTORY` **and** to `owner.history` for the LM client and every module in `settings.caller_modules` (`clients/base_lm.py:29-32`). `caller_modules` is built up in `Module.__call__` and travels through `settings.context` (`primitives/module.py:88-92`); `module.history = []` lives on the object (`module.py:78`).
  - Elixir: a module is an immutable struct — there is no object to append to. Two viable shapes:
    - **(a)** a module identity (an id in the struct) plus a store keyed by it;
    - **(b)** tag each entry in our existing global history (`Dspy.LM.History`) with the caller-module stack, and let `Module.inspect_history(module)` filter by the module's id.
  - Either way, the **caller-module stack must travel with the H0 process context into spawned tasks** (Parallel, Evaluate, optimizers). Otherwise calls made inside tasks are not attributed — that is the H0 invariant again.
  - Struct copies share an id, while Python's `deepcopy` copies the history and then diverges. That's a semantic difference to declare.
  - I'd recommend (b): no new mutable store, reuses the history we already have.
- **F-7. BootstrapFewShotWithRandomSearch is portable exactly.** Seeds `-3` (zero-shot), `-2` (labeled only), `-1` (unshuffled bootstrap), then `0..N-1` (`teleprompt/random_search.py:75-107`). Each seed uses a fresh `random.Random(seed)` for `shuffle` and `randint` (`:106-107`). Candidates are scored with Evaluate; a strict `>` keeps the earliest seed on ties (`:136`); `stop_at_score` stops early; candidates are kept sorted by score. **With M1-e's CPython generator (E1) and a `randint` on the same primitive, we get the same candidate sets as Python for the same seed.** Depends on M1-e.
- **F-8. Predict `config` has to exist before save/load means anything.** Upstream `Predict(signature, callbacks=None, **config)` stores `config` and merges it into each call (`predict.py:158`). When `n > 1` and temperature is unset or ≤ 0.15, it raises temperature to 0.7. `reset` clears `lm`, `traces`, `train` and `demos`. `set_lm`/`get_lm` live on Module. Our queue row S038 lists all of these as missing.
